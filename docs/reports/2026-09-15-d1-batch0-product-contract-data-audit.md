Date: 2026-09-15

Status: D1 Batch 0 complete; source, contract, migration, image, e2e, and live

Authority: evidence for D1 Batch 0 in

## Scope

The audit traced Product behavior across:

- Product Prisma schema and all three migrations;
- Product HTTP DTOs/controller and gRPC DTOs/controller;
- Product service validation, mapping, lifecycle, discounts, and gallery logic;
- Taxonomy and Settings dependencies;
- Media schema, policy surface, and the existing admin `GetById` contract;
- gateway route manifest, input profiles, DTOs, Product adapter, and OpenAPI;
- generated `@nebula/api-client` types and focused consumer tests;
- root development seed tooling;
- Product and gateway unit/e2e test inventories;
- current Product, Order, Media, Settings, and Taxonomy documentation.

The unrelated Realm Auth R6.1 experiment was excluded from the Product source
audit. A later baseline build exposed its incomplete compile state; its content
was not modified and is preserved in the named path-scoped stash recorded
below.

## Result

The external path is already broad enough for D1. It exposes public Product and
gallery reads plus admin list/get/create/update/delete/restore/hard-delete,
bulk-discount, and gallery management through the gateway and generated client.
The immediate work is domain correctness and contract repair rather than adding
another transport or frontend.

The strongest mechanisms to preserve are:

- public Product and gallery reads enforce `ACTIVE` plus non-deleted state in
  Product service;
- gateway repeats the public visibility check and rejects widened downstream
  replies;
- admin Product routes require both the `admin-web` application profile and an
  `admin` or `root-admin` actor;
- Product gRPC writes repeat role policy at the owning service;
- gateway input profiles reject undeclared fields and separate public/admin
  list controls;
- gateway mutations require an idempotency key and use shared Redis-backed
  response replay;
- sparse Product patches preserve omitted proto3 scalars because Product gRPC
  uses `defaults: false`;
- Product owns no Taxonomy or Media database foreign key; cross-service access
  uses typed contracts and signed S2S context;
- the obsolete cross-database category foreign key was removed by migration;
- default product category initialization is bounded, retried, and backed by
  Taxonomy plus Settings rather than a duplicate local category table.

## Current Contract Path

```text
external client
-> generated @nebula/api-client
-> /api/v1 gateway route + input profile + idempotency policy
-> GatewayProductApiService mapper
-> signed ProductService gRPC
-> ProductServiceImpl
-> product-owned Postgres
     |-> signed TaxonomyService reads
     `-> signed SettingsService reads
```

Media is not part of this path today. Product persists unverified URL strings.

## Confirmed Defects And Implementation Gaps

### D1-001 - Missing Stock And Availability

Classification: confirmed implementation gap.

Product has no stock, inventory-tracking, availability, or purchasability field.
`ACTIVE` is therefore the only commercial/public readiness signal. D1 cannot
give D2 an authoritative stock check until this is implemented.

### D1-002 - Missing Variants And Selected Options

Classification: confirmed implementation gap.

No Product variant, option definition, variant SKU, price override, stock, or
variant Media relationship exists. D2 currently has only `productId`, so it
cannot snapshot a selected variant.

### D1-003 - `effectivePrice` Is A False External Fact

Classification: confirmed defect.

`Product.effectivePrice` exists in protobuf, gateway DTO, OpenAPI, and generated
client, but `ProductServiceImpl.toDto` never returns it. The gateway gRPC client
loads defaults, so the missing scalar becomes `0`. A product priced at 100 can
therefore be advertised externally with `effectivePrice: 0`.

### D1-004 - Discount State And Wire Representation Are Inconsistent

Classification: confirmed defect.

- Product with no discount returns an empty internal string, while OpenAPI and
  the generated client promise `PERCENTAGE | FIXED | NONE`.
- Single-product patching `discountType: NONE` does not clear value, active
  state, or dates, although bulk clearing does.
- A write can retain or create active discount state without a valid type.
- Updating only one date does not compare it with the stored opposite date.
- Percentage discounts are bounded by the generic one-million maximum rather
  than 100.

### D1-005 - Price Requiredness Differs By Entry Path

Classification: confirmed defect.

The direct Product HTTP service rejects a missing price because validation
reaches `assertPrice(undefined)`. Gateway/OpenAPI marks price optional and the
gateway converts omission to zero before gRPC. The two supported entry paths
therefore disagree about whether zero-price creation must be explicit.

### D1-006 - Currency Has Multiple Authorities

Classification: confirmed defect.

Settings seeds `USD`, Product database defaults to `EUR`, Product response has
an `EUR` fallback, Product accepts any short caller string, and a transient
Settings error causes Product to cache `USD` for the remainder of the process.
Order later derives cart currency from the first Product. There is no single
validated shop-currency rule.

### D1-007 - Taxonomy Relationships Are Incomplete

Classification: confirmed implementation gap.

Category validation is authoritative and should remain. Tags are free-form
strings, and brand has no Product reference. The Product Taxonomy facade can
address kinds such as `brand` and `tag`, but the Product model cannot bind those
records.

### D1-008 - Product Treats Media URLs As Authority

Classification: confirmed implementation gap.

Product stores and publicly returns arbitrary thumbnail/gallery URLs. It cannot
prove that a referenced Media record exists, is `READY`, is public, passed its
scan policy, or remains renderable. This bypasses Media-service ownership.

The current Media `GetById` RPC is admin-only and returns facts, but asking
Product to interpret those facts would duplicate Media eligibility policy. The
narrow correction is one internal Media-owned reference-resolution operation
that answers whether a Media ID is eligible for a named public Product role and
returns the stable render identity needed by Product. Product then stores Media
IDs and roles rather than credentials or provider URLs.

Compatibility/migration cost:

- additive Product thumbnail/gallery Media-ID columns or replacement rows;
- a temporary read-compatible legacy URL field during backfill;
- deterministic mapping only for legacy URLs that can be proven to identify an
  existing Media record;
- explicit unresolved-row reporting rather than guessing;
- one versioned Media RPC, typed client method, Product client module, failure
  mapping, and migration/rollback proof.

A plain Product-side URL validator is narrower in code but insufficient because
it cannot enforce current Media lifecycle/privacy policy.

### D1-009 - Slug/SKU Mutation Is Nondeterministic And Race-Prone

Classification: confirmed defect.

Generated identifiers query before insert without a concurrency retry. A
caller-provided duplicate SKU is silently rewritten with a random suffix, while
an explicit duplicate slug reaches the database error path. Patch values are
not normalized like create values. The API has no declared conflict contract
for these cases.

### D1-010 - Admin Updates Have No Lost-Update Protection

Classification: confirmed implementation gap.

Product has `updatedAt` but no version or conditional write. Two valid admin
patches can overwrite each other without either caller learning that its base
state was stale. Gateway request idempotency prevents replay duplication; it
does not solve concurrent edits with different keys.

### D1-011 - Omitted Gallery Sort Does Not Append Through Gateway

Classification: confirmed defect.

Product service appends when `sort` is absent. Gateway maps an absent external
sort to proto scalar `0`, so multiple ordinary additions arrive with zero and
skip append behavior. The external and owning-service semantics disagree.

### D1-012 - Destructive And Missing-Parent Semantics Are Incomplete

Classification: confirmed defect.

Admin gallery list can return an empty collection for a missing Product because
it does not check the parent. Hard deleting a Product with dependent gallery,
attribute, comment, or hotspot rows can hit a foreign-key restriction, while
Prisma `P2003` is not mapped to a stable domain error. Whether hard deletion
belongs in B0 also lacks an explicit retention decision.

### D1-013 - Current Demo Seed Cannot Prove B0

Classification: confirmed implementation gap.

The root demo seed is safely refused in production and is repeatable for its
two records, but it calls Auth, Product, and Blog services directly. It creates
only one active base Product and does not reset state or prove gateway policy,
variants, lifecycle, Taxonomy/Media relationships, conflicts, or denials.

### D1-014 - Tests Protect Boundaries But Miss Commercial Rules

Classification: confirmed evidence gap.

The passing tests cover validation transport parity, public/admin visibility,
category error translation, selected gateway mapping/policy, and minimal e2e
create/read/update/delete. No focused evidence was found for effective price,
discount invariants, currency recovery, identifier collisions, concurrency,
bulk discount, restore/hard-delete dependency behavior, complete gallery
ordering, variants, stock, or Media-reference validity.

## Stale Implementation Or Documentation

- `docs/services/product-service.md` describes missing HTTP delete/gallery
  routes without clearly distinguishing internal Product HTTP from the complete
  external gateway surface.
- The protobuf Product input comment says status defaults to `ACTIVE`; service
  creation intentionally defaults to `DRAFT`.
- Prisma retains an `ACTIVE` database default even though normal service create
  writes `DRAFT` explicitly.
- `promoStart` and `promoEnd` remain database fields without current input or
  output ownership.
- F3 live proof calls only anonymous Product list; it does not prove Product
  administration or an ecommerce transaction.

## Optional Hardening

These are not current D1 requirements unless implementation evidence promotes
them:

- database check constraints duplicating already complete service invariants;
- public lookup by slug before a client requirement needs it;
- cursor pagination or specialized Product search indexes;
- removing all advanced Product fields from the current response in one
  breaking change;
- bulk discount if the basic admin workflow does not require it;
- general-purpose product sets, comments, reviews, recommendation graphs, or
  promotion scheduling.

## Future Scaling Considerations

- tenant/site-scoped SKU, slug, taxonomy, currency, and Media relationships are
  resumed F4 work;
- reservation across warehouses, backorders, fulfillment, real payment, tax,
  refunds, and advanced inventory remain M1;
- derived Media lifecycle, file-manager UI, and CDN processing remain F5;
- storage-provider topology remains M3S/F9;
- generalized Product search, events, outbox, and shared workers remain M6
  unless an earlier concrete operation needs a bounded local mechanism.

## Narrow D1 Implementation Order

1. Repair existing false/inconsistent facts without schema expansion:
   effective price, discount representation/invariants, price requiredness,
   currency normalization, gallery append semantics, identifier conflicts, and
   stable destructive-operation errors.
2. Add commercial Product state with migrations: basic stock/availability,
   explicit concurrency version, bounded variants/options, and deterministic
   identifiers.
3. Add authoritative Product Taxonomy relationships for the selected category,
   tags, and brand scope.
4. Add the Media-owned reference resolver and Product Media-ID/role migration
   with a bounded legacy compatibility window.
5. Extend protobuf, Product service, gateway DTO/mapping, OpenAPI, and generated
   client together; do not hand-edit generated artifacts.
6. Add deterministic D1 fixtures, migration proof, focused commercial tests,
   and a gateway-only live Product workflow.

This order fixes facts already promised to callers before adding new fields and
keeps each migration/release checkpoint independently reviewable.

## Stateful Baseline Incidents And Recovery

The first `pnpm backend:boot` attempt on 2026-09-15 exposed a prerequisite
outside Product. Tenant Authority's populated local database applied the R1
control-plane schema and then correctly rejected the R2 actor backfill with
`authority_default_actor_realm_missing`. It contained 34 memberships and one
platform grant but no R1 identity-realm seed records. Prisma's final message,
`current transaction is aborted`, hid that original database error.

Classification: confirmed populated-upgrade/tooling gap. The R2 migration
expects the R1 inactive control-plane seed before it runs, while the generic
boot path runs all migrations before all seeds. Clean empty migration proof is
unaffected because it has no legacy actor rows. This is not a Product contract
failure and does not justify resuming broader F4 implementation.

The local recovery preserved business data: the failed transactional migration
was marked rolled back with the migration-owner connection, the existing
versioned development seed created the two inactive control-plane realms, and
R2 plus the later per-role uniqueness migration then applied normally. Direct
checks found zero missing realm/subject pairs across all 34 memberships and the
platform grant. Tenant Authority migration status passed, and its seed rerun
returned `ALREADY_CURRENT` for both the default authority and identity control
plane. The ignored local Tenant Authority `.env` was brought up to date with
the checked-in development-only signing variables; no tracked secret or
production value changed.

The general populated pre-R2 boot-order gap remains recorded for a narrow
tooling/runbook correction before any comparable deployed upgrade. The current
local database is ready for the ordinary boot retry.

The second `pnpm backend:boot` attempt passed migration/seed work and reached
the shared backend image build. That build stopped in
`@nebula/realm-auth-service` because the following paused, untracked R6.1 files
were included in the Docker build context:

- `apps/realm-auth-service/prisma/verify-r6-default-session.ts`;
- `apps/realm-auth-service/src/session/`;
- `apps/realm-auth-service/test/realm-session-crypto.spec.ts`;
- `apps/realm-auth-service/test/realm-session-service.spec.ts`.

A focused local Realm Auth build reproduced seven `TS2339` errors in
`src/session/realm-session.service.ts`: two calls to missing
`reconcileSession`, three to missing `removeSession`, one to missing
`rotateSessionCache`, and one to missing `removeSessions` on
`RealmAuthRedisService`. The outer `backend_image_user-service_failed` message
was only the name of the shared image target; Realm Auth was the compiler that
failed.

Classification: unrelated incomplete implementation in preserved user work.
Completing these Redis/session methods would resume deferred F4 R6.1 and is
outside D1. It is not a defect in the committed backend or Product contract.

Before containment, Salar required this failure to be logged. The authorized
containment is a path-scoped Git stash named
`paused-f4-r6.1-before-d1-baseline-2026-09-15`, containing only the four paths
above. This keeps the experiment byte-for-byte recoverable and removes it from
the build context without changing committed Realm Auth behavior. Restore it
later with `git stash apply` after selecting that named stash; do not drop the
stash until resumed F4 work is safely committed.

Containment result: the named stash was created successfully and its inventory
contains exactly the nine untracked files under the four paths above. No
tracked file entered the stash. With the experiment absent from the working
tree, `pnpm --filter @nebula/realm-auth-service build` passed. This proves the
committed Realm Auth package is buildable and isolates the previous compiler
failure to the paused experiment.

The third boot attempt passed those source checks but failed in Docker build
step 14 while `pnpm install` ran workspace postinstall scripts. User, Realm
Auth, Tenant Authority, Settings, and Media all started `prisma generate`
concurrently. After roughly 325 seconds, all five TLS connections ended with
the same `ECONNRESET`/`Error: aborted`; pnpm then reported each postinstall as
failed. No TypeScript, Prisma schema, migration, or application-runtime error
appeared in this attempt.

Classification: confirmed Docker build reproducibility defect. The shared
Dockerfile requires the Prisma postinstall generators but allowed pnpm's
default parallel lifecycle execution to create five simultaneous engine
download paths. Retrying the same uncontrolled concurrency could succeed by
chance and would not correct the failure mode.

The narrow correction keeps the existing postinstall mechanism and adds pnpm's
supported `--child-concurrency=1` flag to the build-stage dependency install.
It serializes lifecycle scripts without changing package resolution, the
lockfile, generated client ownership, runtime images, or production dependency
stage. The material cost is a slower uncached install; the lockfile/manifests
still own the cached dependency layer. A backend-tooling assertion now prevents
the serial limit from disappearing. `pnpm test:backend-tooling` passed all 55
tests with that assertion. The later successful boot proved the serialized
postinstall layer in Docker.

The fourth boot attempt proved that correction: build step 14, including the
serialized Prisma postinstalls, was cached, the shared compilation was cached,
and `media-service` image 6/11 exported successfully. The following
`taxonomy-service` build then resolved both mutable Node base tags to different
index digests than the immediately preceding media build. That invalidated the
base layer and reran `corepack prepare`; its request for the pinned pnpm tarball
failed before application compilation. The parallel `apt-get` runtime-base
step also showed repository connection retries and was cancelled only because
Corepack failed first.

Classification: confirmed Docker base/dependency reproducibility defect. The
sequential image runner is working as designed for Docker Desktop resource
control, but mutable `node:22-bookworm` and `node:22-bookworm-slim` tags allowed
different service targets in one run to build from different bytes and repeat
cold network setup.

The narrow correction pins both existing official Node 22 Debian Bookworm
image indexes by digest. It also gives Corepack a shared locked BuildKit cache
and three bounded attempts to prepare the already-pinned pnpm 10.17.1. This
does not replace the base family, package manager, shared Dockerfile, or
sequential runner. The maintenance cost is explicit base-digest updates rather
than automatic tag movement; each update requires backend image and security
scan evidence. Static tooling now asserts immutable build/runtime bases, the
Corepack cache, and bounded retry. All 55 backend-tooling tests pass, and
`docker buildx build --check --file docker/backend.Dockerfile .` reports no
warnings. The final backend boot completed across this pinned build graph.
